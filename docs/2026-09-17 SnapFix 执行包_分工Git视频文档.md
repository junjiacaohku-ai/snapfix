## 2. Git 工作法(轻量 trunk-based)

**仓库**:GitHub **private** 单仓 monorepo(交付前不开源):

```
/app      ← Flutter
/server   ← FastAPI
/docs     ← 调研表、契约、会议纪要、最终文档
/landing  ← landing page(展示用)
```

**规则(一句话版)**:
- `main` 永远可跑可演示;任何人不直接 push main(GitHub Settings → Branches 开 protection:需 1 个 approving review)
- 短分支 `feature/扫描页`、`fix/上传超时`,活不过 3 天,合完即删
- PR 小步(<300 行),描述写"做了什么+怎么验证(截图)";review 轮值两人,24h 内看;squash 合并
- 每天下班前 push(WIP 也推自己分支);改 `pubspec.yaml`/路由/契约文件前群里喊
- 每周 rebase main;每周四打一个 tag(`demo-w4`…),演示前 freeze `demo-final`
- commit 前缀:`feat:` / `fix:` / `docs:` / `chore:`

**为什么这样够**:5 人 2 个月,gitflow 是仪式感负担;"main 可跑+PR 有人看"拿走 80% 价值。git log 到期末就是"各成员贡献"的证据链。

## 3. 演示视频方案(15 分,1-2 分钟)

**形态**:模拟器录屏主线(干净无弹窗)+ 10 秒 AI 片头点缀 + 字幕 + 配音(或纯字幕)。**绝不用桌面播放器播录屏**(往届反面教材)。

**90 秒分镜脚本**:

| 时间 | 画面 | 字幕/配音 |
|---|---|---|
| 0-8s | AI 片头:坏掉的电器快剪 + 片名 SnapFix | "东西坏了,先别急着叫师傅" |
| 8-20s | 场景 1:IKEA 组装卡壳 → 拍照 → 分析中过程页 | "拍一张照,它认得这是什么" |
| 20-40s | 诊断结果:设备卡 + 分步+引用展开 | "每一步都有说明书出处,不是瞎编" |
| 40-50s | 三档决策卡:自己修/找房东/找师傅 | "它还告诉你,这事该不该自己上手" |
| 50-62s | 安全门:微波炉 → 拒答页 | "高压危险?它坚决不教你修" |
| 62-75s | 报修助手:生成中英双语报修信息 → 分享 | "修不了,一键生成报修信,房东秒懂" |
| 75-90s | 维修档案回看 + 片尾 logo + 组员名单 | "SnapFix — 先搞懂,再决定" |

**制作安排**:FE-2 主剪;11/19 演示现场录屏留素材;11/20-26 剪辑;配音粤语/普通话均可,字幕必须英文(老师看得顺)。

## 4. 交付文档方案(15 分,≥2 页)

结构(对应任务书三要件):

1. **Background Research**(≈1 页):调研对比表(直接搬 `2026-09-17 SnapFix 市场调研与竞品分析.md` 第 6 节)+ 一段结论(市场空缺→motivation)

3. **Contributions**(≈0.5 页):按人列点,与 git log/PR 记录互证——**从现在起每周纪要写进 /docs**

语言:英文(课程交付);图表:管线图 + 信息架构图 + 2-3 张 App 截图。
