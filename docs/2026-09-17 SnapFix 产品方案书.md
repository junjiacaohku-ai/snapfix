## 1. 产品概述

- **名称**:SnapFix(随手修)
- **一句话**:拍一张照片,告诉你东西哪坏了、能不能自己修、怎么修、修不了怎么报修。
- **类别**:Information / 生活工具(任务书类别:Information)
- **形态**:Flutter 双端 App(iOS + Android)+ FastAPI 后端
- **Slogan**:先搞懂,再决定。 / Snap it. Fix it. Or report it.

**与竞品的本质区别**:诊断类工具(iFixit、FixIt Lens、通用 AI)止步于"告诉你怎么修";SnapFix 面向**港漂学生/租房青年**,把"拍照诊断 → 修理决策 → 报修闭环"做成一个完整场景(差异论证见市场调研文档第 6、7 节)。

## 2. 背景与问题

**目标用户**:在港就读学生、租房青年(我们自己就是)。

**痛点**(证据见市场调研):
1. 东西坏了,说明书找不到,通用 AI 只给泛泛建议("重启试试"),不认识具体型号
2. 不知道自己能不能修——高压电、燃气乱动有真实危险;请师傅又怕被宰(维修平台乱收费已成社会新闻)
3. 决定报修后,跟房东/物业描述不清楚问题,中英文夹杂说不清

**机会**:多模态大模型 + 手册检索增强(RAG)已能让"拍照诊断"达到可用水平;而"修/不修/报修"的决策与闭环,没有竞品做。

## 3. 目标与衡量

| 层级 | 目标 | 衡量 |
|---|---|---|
| 课程目标 | 11/19 课堂演示完整流程不翻车;文档/视频/演示拿满 35% | 演示当天 mock 兜底可用;视频 ≤2 分钟看完核心流程 |

## 6. 功能详述

### F1 拍照诊断(Must)
- **描述**:拍摄或从相册选择照片 → 上传 → 返回结构化诊断(设备类别/品牌型号/可见故障/置信度)。
- **交互**:扫描框引导构图;质量不合格(过暗/过糊)即时提示重拍;上传后进入"分析中"过程页(展示管线阶段:识别中→查手册→安全评估→生成步骤)。
- **异常态**:识别置信度低 → 引导 F1b 手动输入;无网络 → 提示切换 mock 演示模式。
- **验收**:6 个演示场景中 5 个正确识别设备类别与故障方向。

### F1b 错误码速查(Must,降级旁路)
- 输入品牌 + 错误码(如 "Bosch E24")→ 跳过视觉识别直接进入检索诊断。

### F2 分步指导(Must)
- **描述**:诊断结果下方给出有序步骤,每步含:操作说明、注意事项、**来源引用**(手册名+章节)、完成/没用/跳过反馈按钮。
- **异常态**:引用校验失败的步骤不展示(宁缺毋假)。
- **验收**:每个步骤可展开看引用原文;反馈按钮状态持久化。

### F3 安全门(Must,不可砍)
- **描述**:规则分类器先于生成执行;命中高危类目(高压电、燃气、电容放电等)→ 不出任何步骤,只显示拒答说明 + 专业求助建议 + 风险解释。
- **验收**:高危测试集 100% 拒答;正常类目不误伤。

### F4 三档决策(Must)
- 每个诊断结论给出:① 适合自己修(难度/工具/预估时间)② 建议找房东(非破坏性、责任在房东)③ 必须找师傅(高危/需资质),并给一句话理由(可解释页)。

### F5 报修助手(Should)
- 基于诊断结果一键生成报修信息:问题描述、设备信息、照片、已尝试步骤;**中英双语**两个版本;一键复制/系统分享。

### F6 维修档案(Should)
- 历史诊断列表(设备、结论缩略、日期);点击进入详情;可单条删除。

### F7 说明书柜(Could,V1.1)
- 用户上传自家说明书(拍照/导入 PDF)→ 后端切块索引 → 检索时优先命中。

## 7. 信息架构与页面流

```
启动 → 首页(扫描入口 + 维修档案入口 + 错误码速查入口)
  ├─ 扫描页 → 预览/质量检查 → 分析中(管线阶段动画)
  │     → 诊断结果页(设备卡 + 决策卡 F4 + 分步列表 F2)
  │        ├─ 步骤详情(引用原文展开)
  │        ├─ 安全拒答页(F3 命中时替代结果页)
  │        └─ 报修助手(F5,中英双语预览 → 复制/分享)
  ├─ 错误码速查页(F1b)→ 诊断结果页(同上)
  └─ 维修档案(F6)→ 历史详情(同结果页只读)
```

底部 Tab:**扫描 / 档案 /(V1.1 说明书柜)**。全局主题:深空蓝底 + 琥珀色主行动色(修理工具感),圆角卡片,大字号步骤。

## 8. AI 管线设计(后端)

```
照片 → ①质量门(分辨率/亮度/模糊度)
     → ②Vision 提取(多模态 LLM,结构化 JSON:设备/品牌/型号/错误码/可见故障)
     → ③归一化(品牌别名映射、错误码正则)
     → ④手册检索(BM25 起步,按设备类别+错误码加权;V1.1 可换向量检索)
     → ⑤安全门(规则分类,命中即短路拒答)
     → ⑥步骤生成(LLM,约束:只能引用检索到的手册片段)
     → ⑦引用校验(无法对应手册片段的步骤丢弃)
     → ⑧持久化(会话/档案/反馈)+ 返回
```

**Provider 策略**:Gemini(aistudio 免费额度)主用 → OpenAI 兼容接口兜底 → **mock 确定性模式**(无 key 全管线可跑,演示/测试/CI 用)。Key 只存后端 `.env`。
**降级矩阵**:相机不可用→相册;vision 失败→F1b 手动;检索空→通用建议+明示"未找到手册引用";生成失败→mock 步骤(标注演示数据)。

## 9. 数据模型草案(SQLite)

- `sessions(id, device_category, brand, model, error_code, image_path?, decision, created_at)`
- `steps(id, session_id, idx, content, citation_manual, citation_section, feedback)`
- `manuals(id, title, source, category, created_at)` / `manual_chunks(id, manual_id, idx, text)`
- `reports(id, session_id, lang, content, created_at)`

## 10. API 契约草案(v1)

- `POST /api/analyze/image`(multipart 照片)→ 诊断会话
- `POST /api/diagnose/manual`({brand, error_code})→ 诊断会话
- `GET /api/sessions` / `GET /api/sessions/{id}` / `DELETE /api/sessions/{id}`
- `POST /api/sessions/{id}/steps/{step_id}/feedback`
- `POST /api/sessions/{id}/report`({lang})→ 报修文本
- `POST /api/manuals`(V1.1 说明书柜上传)
- `GET /api/health`(含 provider 状态,mock 标记)

## 11. 非功能需求

- **性能**:诊断端到端 ≤30s(演示场景 mock ≤3s)
- **隐私**:照片处理后即删,不持久化原图;档案可整清;无账号无追踪
- **合规**:拒答类目表是责任底线;App 内明示"非专业诊断,仅供参考"
- **可用性**:全流程 ≤3 次点击出诊断;步骤字号 ≥16pt
